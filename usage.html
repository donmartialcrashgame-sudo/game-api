01 · Overview

What Gaming API is

Gaming API is a developer-facing foundation for live gaming features. The current site combines a public live-game presentation, account authentication and a protected developer dashboard. The homepage is intentionally view-only: it can display live round information without exposing betting controls or private credentials.

LIVEReal-time events

Use an event-driven WebSocket architecture when your application needs round state changes without constant polling.

AUTHProtected accounts

Account features are handled through authenticated sessions, with support for stronger factors such as MFA and passkeys.

FRONTENDPresentation layer

Keep browser code responsible for displaying data. Authoritative game logic and secrets should remain server-side.

Important: The public documentation describes the current frontend architecture. Do not treat example URLs, event names or payloads below as a guarantee of a production API contract unless those values are published by your backend.
02 · Quick start

Get your integration organized

A reliable integration starts by separating public configuration from secrets and by treating the server as the source of truth.

01

Create an account

Open the sign-up flow, verify your email when required, then enter the protected dashboard.

02

Secure the account

Add a passkey or Google Authenticator from the security flow. MFA should be preferred for developer accounts that control production integrations.

03

Choose your integration layer

Use normal HTTPS requests for request/response operations and WebSocket events for continuously changing game state.

04

Keep credentials off the browser

Private API secrets belong in your server environment. Never hard-code privileged keys into HTML, JavaScript bundles or public repositories.

Browser-safe configuration pattern
const API_BASE_URL = 'https://game-api.online';

// Public configuration only.
// Keep private API keys on your server.
const config = {
  baseUrl: API_BASE_URL,
  transport: 'https + websocket'
};
03 · Authentication

Protect identity before API access

The current dashboard checks the authenticated Supabase session and displays the account email and authenticator assurance level. The project also contains dedicated flows for MFA setup, MFA verification, passkey setup and OAuth-style sign-in providers.

Recommended account flow

  1. Register or sign in.
  2. Verify the account where required.
  3. Check the active session before loading protected data.
  4. Use MFA or a passkey for stronger protection.
  5. Sign out when a shared device is no longer trusted.

Authentication states

StateMeaning
UnauthenticatedNo valid session is available.
AuthenticatedA valid account session exists.
MFA / AAL2A stronger authenticator assurance level has been reached.
ExpiredRefresh or sign in again before protected operations.
Session check concept
const { data, error } = await supabase.auth.getSession();

if (error || !data.session) {
  // Redirect to your sign-in page.
  location.href = '/login.html';
}

// Never place a privileged server secret here.
04 · Requests & responses

Use HTTPS for discrete operations

Request/response APIs are best for operations where the client asks for a specific resource and receives a finite response. Your backend should validate authentication, authorization, input shape and rate limits before performing privileged work.

Request checklist

  • Use HTTPS in production.
  • Send the minimum required fields.
  • Validate values on the server, not only in the browser.
  • Use an idempotency strategy for operations that may be retried.
  • Log a request ID rather than sensitive credentials.

Response checklist

  • Return predictable JSON structures.
  • Use meaningful HTTP status codes.
  • Return machine-readable error codes.
  • Never return private secrets.
  • Include enough information for safe retry decisions.
Generic request pattern
const response = await fetch(`${API_BASE_URL}/your-endpoint`, {
  method: 'GET',
  headers: {
    'Accept': 'application/json'
  }
});

if (!response.ok) {
  throw new Error(`Request failed: ${response.status}`);
}

const data = await response.json();

Replace /your-endpoint with an endpoint that your backend actually exposes. The frontend repository currently does not publish a complete REST endpoint catalog, so invented endpoint paths should not be copied into production.

05 · Live WebSocket

Subscribe to changing game state

The public homepage is designed around a live WebSocket game monitor. A WebSocket is useful when the server needs to push round lifecycle changes to connected clients without requiring a new HTTP request for every update.

This console performs a lightweight health check against the public website and updates the clock automatically. It does not pretend to be a connection to a private game WebSocket. Your application should connect to the actual WebSocket endpoint supplied by your backend configuration.

Recommended WebSocket lifecycle

Connect

Open one connection per application context where practical. Avoid creating a new socket on every render.

Subscribe

After connection, send only the subscription message required by your published protocol.

Reconnect

Use bounded exponential backoff with jitter when the connection closes unexpectedly.

Generic WebSocket client pattern
const socket = new WebSocket('wss://YOUR-PUBLISHED-WS-ENDPOINT');

socket.addEventListener('open', () => {
  console.log('connected');
});

socket.addEventListener('message', (event) => {
  const message = JSON.parse(event.data);
  // Validate the message before rendering it.
  console.log(message);
});

socket.addEventListener('close', () => {
  // Reconnect using bounded backoff.
});
06 · Event model

Design around round lifecycle events

A crash-style game commonly has a lifecycle such as waiting, running and crashed/settled. Your frontend should render the state it receives instead of trying to calculate an authoritative crash value locally.

ConceptPurposeClient behavior
Round IDUniquely identifies a round.Use it to correlate updates.
StatusDescribes lifecycle state.Change the UI according to the received state.
MultiplierCurrent displayed game value.Render the server-provided value.
TimestampOrders or measures events.Use it for diagnostics and synchronization.
SettlementMarks the completed round.Move the round into recent history.
Authority rule: the browser is not the source of truth for game outcomes. Never let a client-side multiplier, timer or animation determine a financial or game result.
07 · Security

Build the secure boundary first

Never expose

  • Service-role or administrative keys.
  • Database passwords.
  • Private signing secrets.
  • Payment provider secrets.
  • Privileged internal endpoints.
  • Recovery codes in logs or analytics.

Always validate

  • Authentication and session freshness.
  • User authorization for each protected resource.
  • Input type, length and allowed values.
  • Origin and transport requirements where applicable.
  • Rate limits and abuse controls.
  • Server-side game state before sensitive actions.

The existing dashboard also provides a path toward stronger account security through Google Authenticator TOTP/MFA and passkeys. These controls protect the account; they do not replace server-side authorization for API operations.

08 · Errors & retries

Make failures predictable

SituationRecommended action
401 / unauthenticatedRefresh the session or send the user through sign-in.
403 / forbiddenDo not retry blindly; check permissions and account state.
404 / not foundVerify the endpoint and resource identifier.
409 / conflictResolve state conflict or use an idempotency key where supported.
429 / rate limitedRespect retry information and back off.
5xx / server errorRetry safe/idempotent operations with bounded exponential backoff.
WebSocket closeReconnect with jitter; do not create unlimited simultaneous sockets.
Simple bounded backoff
let attempt = 0;

function nextDelay() {
  const base = Math.min(30000, 1000 * 2 ** attempt++);
  const jitter = Math.random() * 500;
  return base + jitter;
}

// Reset attempt = 0 after a successful connection.
09 · Production checklist

Before you ship

Frontend

  • Use HTTPS and WSS.
  • Keep public configuration separate from secrets.
  • Handle loading, empty, error and disconnected states.
  • Clean up WebSocket listeners on page/component disposal.
  • Do not calculate authoritative game outcomes locally.

Backend

  • Authenticate and authorize every protected operation.
  • Validate all client input.
  • Rate-limit public and authenticated endpoints.
  • Log request IDs and operational errors without sensitive data.
  • Keep game state authoritative on the server.

Operational monitoring

Track connection counts, WebSocket disconnects, event delivery failures, HTTP latency, error rates and authentication failures. Alert on sustained changes rather than isolated client-side errors.

10 · FAQ

Frequently asked questions

Is the public homepage an API key or developer console?

No. The homepage is a public presentation layer. Private account and developer features belong behind authentication.

Can I put a private API key inside JavaScript?

No. Anything shipped to a browser should be considered visible to the user. Put privileged credentials on your server.

Should I poll the game every second?

Not when a supported WebSocket event stream is available. Prefer server-pushed events for continuously changing state.

Does the documentation page generate game results?

No. It only demonstrates integration patterns and performs a lightweight public-site health check. It does not generate or predict crash outcomes.

Where do I find the exact production WebSocket URL?

Use the endpoint configured and published by your backend. The current frontend repository does not expose a complete public endpoint contract, so this page intentionally uses a placeholder rather than inventing one.

How should I handle a disconnected client?

Show a clear disconnected state, stop rendering stale data as current, reconnect with bounded backoff, and resynchronize state after reconnecting.
